# v2 多矿机页面与服务端队列修复

本次只修改网页、只读报价呈现和部署台 journal，不修改已部署的 Solidity 或合约清单。

- 预算项目创建入口始终向已核验的运营钱包显示。创建时不锁定具体 NFT；募满后可按每批 1–20 台的预算队列逐台采购，同一个父项目共 100 份。
- 采购队列改为钱包会话绑定的 SQLite 服务端记录；跨页面和服务重启按 `account + parent` 恢复，CAS 版本冲突拒绝覆盖，未知交易不能由另一个队列顶替。页面不再将采购队列存入 `localStorage`。
- 创建表单指出具体缺失的金额；展示 Firsto 最新日产能参考价，并明确区分 `BNB / (BEM / 天)` 与合约的 `BNB / H` 上限。不能把日产能价 9 直接当成合约单位算力上限 9，否则会误放大可购价格。现有合约尚不能强制执行日产能价约束；该能力需要独立合约升级与新部署验收。
- 使用的还是已核验的原有合约产物摘要；页面、API 变更不会自动授权购机或发送钱包交易。

验证：`npm run check --prefix web` 全部 277 项通过；预算队列、服务端重启/CAS、创建表单共 16 项定向测试通过；Web 静态构建和部署台构建通过。发布包测试使用规范化临时目录，以便 macOS `/tmp` 与 `/private/tmp` 的路径别名不产生误报。

仍需用户钱包对旧 Factory `0xcB24E7F96D81037086A268d6ea63c53f91D412A2` 执行 `pauseCreation(true)`，使新项目签名前的链上停建门禁满足条件。当前服务端不会绕过这一门禁。
